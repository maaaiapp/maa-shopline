IMPLEMENTATION BLUEPRINT

Implementation blueprint for the real iOS application

The visual and interaction system — The Instrument — is locked. This document specifies what must be built behind it: navigation, components, states, data contracts, dependencies and the boundary between real integration and demo data. It is a product and UX implementation plan. It does not reinterpret the signed Development and Referral Agreement or the proposal scope, and where a capability is not established by the agreement, the proposal or the prototype, it is marked TBD · REQUIRES TECHNICAL VALIDATION rather than assumed.

One correction to the approved spec

The MVP set approved in the Product Spec — 01–06, 08–11, 13, 14, 16, 17, 20–27, 29, 30 — enumerates to 24 rendered states, not 22; my earlier count was wrong. Two states belong with them. 07 (Home — Arabic) was already approved to ship in MVP as the localisation proof, and 28 (Explainable Answer) must be in MVP because AI Growth Advisor cannot be a flagship experience without it — only its deep reasoning-weight editing was deferred. 24 + 07 + 28 = 26 rendered states. Nothing has been added or cut beyond 28.

3 · Navigation architecture

  • Root: conditional. Unauthenticated or unconnected → onboarding stack (01→02→03→04→05). Connected → tab container.
  • Tab container: five tabs — Home, Intelligence, Opportunities, Create, Advisor. Each tab owns an independent navigation stack; state persists across tab switches.
  • Home stack: 06 → 08 / 09 / 10 → 29 → 30. Settings live inside Home, not as a sixth tab.
  • Intelligence stack: 11 → 13 / 14.
  • Opportunities stack: 16 → 17. Evidence and prioritisation are in-screen disclosure on 17, not pushed screens.
  • Create stack: 20 → 21 → 22 → 23 → 24 → 25 → 26. This is the only linear multi-step flow; it must survive backgrounding and be resumable from 20.
  • Advisor stack: 27 → 28.
  • Cross-tab jumps: 09 → 16/17, 14 → 17, 17 → 21, 26 → 16, 28 → 17/21. Each jump switches tab and pushes onto that tab's stack; back returns to the origin screen, not the tab root.
  • Deep links: push notification → 10, 08, 17 or 26. Requires a stable id per insight, opportunity and campaign.
  • Modal layer: confirmation for irreversible actions only — schedule campaign (25), dismiss opportunity (17), disconnect store (30).

AI reasoning and evidence states

  • Confident: claim, confidence mark, evidence fold with sources and weights.
  • Low confidence: claim stated as provisional, with the specific data that would raise it.
  • Insufficient knowledge: no claim made. The data requirement is stated instead. This path is mandatory, not a fallback.
  • Conflicting evidence: both readings shown with their weights; the conflict is surfaced, not resolved silently.
  • Stale reasoning: the claim was generated against data now superseded — marked, with a regenerate action.
  • Generation failed: distinguished from insufficient knowledge; retry preserves context.

7 · Cross-cutting requirements

Authentication and onboarding

  • SHOPLINE OAuth2 plus App Installation Token; tokens in Keychain, never in user defaults.
  • Refresh handled transparently; refresh failure surfaces as the disconnected state, not a silent logout.
  • Install can originate from the SHOPLINE app store — the app must handle an install-initiated launch, not only an in-app connect. Exact entry contract: TBD · REQUIRES TECHNICAL VALIDATION.
  • Multi-store merchants and store switching: TBD · REQUIRES TECHNICAL VALIDATION. Single store in MVP.
  • Onboarding is resumable: interruption at any of 02–05 returns to the same step.

Localisation and RTL

  • English and Arabic. Language is a Settings choice (29), not a debug toggle; appearance follows the system.
  • Full RTL mirroring: layout, navigation direction, back gestures, chart and delta direction, iconography.
  • Arabic-native generation for claims and consequences — not translated English. Where the pipeline cannot yet generate Arabic, the screen says so.
  • Arabic numeral, currency and date formatting; bidi isolation for embedded English product names.
  • MVP scope: 07 fully Arabic; remaining screens English with a stated language notice. Full Arabic is Phase 2.

Notifications

  • APNs. Permission requested at first genuine alert value, not during onboarding.
  • MVP categories: threshold breach (10), campaign scheduled and campaign result ready (25, 26), sync or connection failure (30).
  • Every notification deep-links to a specific screen with a stable id.
  • Per-category preferences are Phase 2 (31). MVP ships a single on/off at the system level.
  • Notification frequency ceiling must exist from day one to protect the "worth interrupting for" standard.
